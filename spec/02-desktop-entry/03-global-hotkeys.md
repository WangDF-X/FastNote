## 1. 目的与范围

定义 FastNote 的全局快捷键（系统级、跨应用可用）注册与管理行为：默认绑定表、冲突检测与提示、平台差异处理、修改流程，确保用户能够在任何场景下通过快捷键快速访问核心功能。

**范围内**: 快捷键表、注册逻辑、冲突处理、平台适配、设置页管理。
**范围外**: 应用内快捷键（SHELL-02）、悬浮球交互（ENTRY-01）。

## 3. 默认快捷键表

| 功能 | Windows/Linux | macOS | 备注 |
| --- | --- | --- | --- |
| 唤起主窗口 | `Ctrl+Alt+F` | `⌃⌥F` | 显示并保持当前路由 |
| 新建任务 | `Ctrl+Alt+N` | `⌃⌥N` | 聚焦 Today 的快速添加框 |
| 新建小记 | `Ctrl+Shift+S` | `⌃⇧S` | 打开快速捕获窗口 |
| 打开日历 | `Ctrl+Alt+C` | `⌃⌥C` | 导航到 Calendar |
| 切换夜间模式 | `Ctrl+Alt+D` | `⌃⌥D` | toggle theme_mode |

> **设计决策 D-31：** 全局快捷键统一使用 `Ctrl+Alt+字母` 或 `Ctrl+Shift+字母` 组合；避免单独修饰键（如仅 `Shift`），降低误触发概率。

- 所有快捷键在注册失败时不阻断启动；在设置页中以 inline error 显示原因。
- macOS 快捷键显示时优先使用符号（`⌃`、`⌥`、`⇧`、`⌘`）。

## 4. 平台实现

### 4.1 Windows

- 使用 `win32::RegisterHotKey` 配合自定义 ID。
- 每个全局快捷键占用一个 hotkey ID；最多支持 16 个并发注册（系统限制）。
- 热键消息通过 `WM_HOTKEY` 投递到应用的隐藏窗口（hWnd 由 platform layer 创建）。
- 注册后自动测试是否成功；失败时记录错误码并返回 false。

### 4.2 macOS

- 使用 Carbon `RegisterEventHotKey` API（legacy 但稳定，macOS 12 仍支持）。
- macOS Sequoia+ 可能要求 UserNotifications permission，但全局快捷键不需要额外权限声明。
- 菜单项右侧显示对应快捷键（如果可用）。

> **已确认（2026-10-26）Q-ENTRY-07：** 允许用户使用 `Shift` 作为唯一修饰键（如 `Shift+F`）吗？→ **当前默认处理：** 允许但有警告（单 Shift 易与系统快捷键冲突），注册时在设置页显示 warning tooltip「可能与系统快捷键冲突」。

> **已确认（2026-10-26）Q-ENTRY-08：** macOS 是否需要请求 Carbon 辅助功能权限才能注册全局快捷键？→ **当前默认处理：** 假设不需要（Carbon 级别不受 TCC 限制）；如果用户报告失败，引导到安全性设置检查。

### 4.3 Linux

- **X11**：使用 `xkb` 底层注册或 GlobalAccord library；注册后监听 `XCB_KEY_PRESS` 事件。
- **Wayland**：不支持全局快捷键（compositor 隔离了键盘事件）。检测到 Wayland 后禁用此能力，并在设置页以 Banner 告知用户。
- KDE Plasma / GNOME Shell 提供各自的 portal 接口，第一版不使用（实现复杂且不稳定）。

## 5. 冲突检测与去重

### 5.1 注册流程

```text
1. 读取设置中的快捷键映射（从 SET-03 获取）
2. 尝试逐一注册每个快捷键
3. 失败时：记录错误 → Toast 告知用户 → 保持该条为未注册状态
4. 全部注册完成后，通知 UI 层更新设置页状态
```

### 5.2 冲突提示

- 如果某个快捷键已被其他应用占用（`RegisterHotKey` 返回 FALSE），Toast 错误提示：「『Ctrl+Alt+F』已被 [应用名] 占用」，并提供「修改」链接跳转到设置页。
- 不自动替换为其他组合。
- 同一应用中两个不同功能的快捷键被设置为相同组合时，只注册第一条，第二条报错。

### 5.3 全局 vs 应用内冲突

- 全局快捷键与应用内快捷键（如 `Primary+1`）**不冲突**：全局只在应用运行时有效，应用不在前台时无效。
- 应用运行时，全局快捷键的优先级高于应用内（因为应用正在接收焦点，需要主动拦截）。
- 如果全局快捷键与当前页面的输入态冲突（如在输入框中按了 `Enter`），应用内规则优先（IME composition active 时不触发）。

> **已确认（2026-10-26）Q-ENTRY-09：** 同一个快捷键（如 `Ctrl+Alt+F`）同时被设为「唤起主窗口」和「新建任务」，会怎样？→ **当前默认处理：** 以最后一次注册为准；先注册的触发后丢弃（通过 250ms 去重窗口过滤重复触发）。建议用户在设置中分配不同的组合。

## 6. 生命周期管理

| 阶段 | 行为 |
| --- | --- |
| 首次启动 | 如果用户从未自定义过快捷键，写入默认值并注册 |
| 设置修改 | 立即注销旧的 → 注册新的 → 成功后保存设置 |
| 切换入口模式 | 快捷键不受影响（独立于 ball/tray） |
| 退出 | 必须注销所有已注册的快捷键（否则残留孤儿 hotkey） |
| 应用恢复（唤醒） | 如果之前有热键注册失败，重新尝试注册 |

## 7. 异常与降级

| 场景 | 处理方式 |
| --- | --- |
| 所有快捷键均注册失败 | Banner 提示「当前环境不支持全局快捷键」，设置页每个条目显示错误 |
| 部分失败 | 成功的照常工作，失败的标记为红色 + 原因文字 |
| Wayland 环境 | 全部禁用，Banner 明确说明 |
| 快捷键被用户手动删除 | 注销该条，设置为空 |

## 8. 验收标准

| 编号 | 验收标准 |
| --- | --- |
| AC-ENTRY-19 | 三平台均可正确注册 ≥3 个全局快捷键，且在不同应用间也能触发。 |
| AC-ENTRY-20 | 快捷键被其他程序占用时 Toast 告知具体被谁占用，设置页显示错误并定位到对应条目。 |
| AC-ENTRY-21 | 在设置页修改快捷键后立即生效（旧组合失效，新组合可用），不影响其他功能。 |
| AC-ENTRY-22 | 退出应用后残留的快捷键被完全注销（重启其他应用不再误触发）。 |
| AC-ENTRY-23 | 输入中文输入法组合期间不触发全局快捷键（Esc 仅取消候选）。 |
| AC-ENTRY-24 | Wayland 下全局快捷键全部禁用，并在设置页有明显标识说明。 |
